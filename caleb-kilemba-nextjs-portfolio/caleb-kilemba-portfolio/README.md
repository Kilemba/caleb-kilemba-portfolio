# Caleb Kilemba — Full-Stack Data Engineering Portfolio, Blog, Booking & Admin CMS

A production-oriented **Next.js 16.3.1** website for **Caleb Kilemba — Data Engineer • Analytics Engineer • Consultant**.

The application replaces the previous Astro + Sanity implementation. It does **not** use Astro, Sanity, WordPress, Contentful, Strapi, or any external CMS. Public content and admin workflows are implemented inside the Next.js project and stored in PostgreSQL.

# Database schema

The Prisma schema includes:

- `AdminUser`
- `AdminSession`
- `Project`
- `Technology`
- `Service`
- `BlogPost`
- `Tag`
- `Booking`
- `Availability`
- `BlockedDate`
- `ContactMessage`
- `Testimonial`
- `SiteSettings`

### Important design choices

**Projects and technologies:** projects can use multiple technologies and a technology can belong to multiple projects.

**Services and technologies:** services use the same reusable technology records.

**Blog tags:** posts and tags have a many-to-many relationship.

**Bookings:** an `activeSlotKey` is unique while a booking is pending or confirmed. This prevents two visitors from reserving the same active consultation slot at the same time. Cancelling or completing a booking releases the key.

**Images:** only image URLs are stored in PostgreSQL. Image binary data is never stored in the database.

**Authentication:** passwords are bcrypt-hashed. Login sessions use cryptographically random tokens. Only a SHA-256 hash of the session token is stored in PostgreSQL; the raw token stays in an HTTP-only cookie.

### Environment variable reference

| Variable | Required | Purpose |
|---|---:|---|
| `DATABASE_URL` | Yes | PostgreSQL connection string |
| `NEXT_PUBLIC_SITE_URL` | Yes in production | Base URL for canonical site links, sitemap and RSS |
| `SESSION_COOKIE_NAME` | No | Admin session cookie name |
| `SESSION_DAYS` | No | Session lifetime in days; defaults to 7 |
| `ADMIN_EMAIL` | No | Optional admin created during seed |
| `ADMIN_PASSWORD` | No | Optional password used only by seed |
| `IMAGE_STORAGE_MODE` | Yes | `local` or `s3` |
| `S3_REGION` | S3 only | Region; Cloudflare R2 uses `auto` |
| `S3_ENDPOINT` | S3 only | S3-compatible endpoint |
| `S3_BUCKET` | S3 only | Bucket name |
| `S3_ACCESS_KEY_ID` | S3 only | Storage API key ID |
| `S3_SECRET_ACCESS_KEY` | S3 only | Storage API secret |
| `S3_PUBLIC_BASE_URL` | S3 only | Public base URL used to display images |
| `S3_FORCE_PATH_STYLE` | No | Usually `false`; some S3-compatible providers require `true` |

Never commit `.env` to Git. It is already excluded by `.gitignore`.

# Booking system

## Visitor workflow

```text
/book
  ↓
Choose published service
  ↓
Enter client details and project problem
  ↓
Choose date
  ↓
Browser requests currently available slots
  ↓
Choose time
  ↓
Server validates the slot again
  ↓
Booking saved as PENDING
```

Server-side validation is authoritative. The visible dropdown alone is not trusted.

## Admin booking statuses

- `PENDING`
- `CONFIRMED`
- `COMPLETED`
- `CANCELLED`

`PENDING` and `CONFIRMED` reserve the slot. `COMPLETED` and `CANCELLED` release the active slot key.

# Image uploads

## Local development

Use:

```env
IMAGE_STORAGE_MODE="local"
```

Admin uploads are written under:

```text
public/uploads/
```

This works on your Windows development machine.

**Do not use local filesystem uploads as permanent production storage on serverless hosts such as Vercel.** Deployments may use ephemeral or immutable filesystems.

## Production: S3-compatible storage

Set:

```env
IMAGE_STORAGE_MODE="s3"
S3_REGION="auto"
S3_ENDPOINT="https://YOUR-S3-ENDPOINT"
S3_BUCKET="caleb-portfolio"
S3_ACCESS_KEY_ID="..."
S3_SECRET_ACCESS_KEY="..."
S3_PUBLIC_BASE_URL="https://images.yourdomain.com"
S3_FORCE_PATH_STYLE="false"
```

The adapter uses `@aws-sdk/client-s3`, so it works with AWS S3 and compatible providers.

### Cloudflare R2 example

Cloudflare R2 exposes an S3-compatible API. As verified in August 2026, its Standard storage free tier includes 10 GB-month per month, one million Class A operations and ten million Class B operations, with Internet egress listed as free under the documented pricing model. Always re-check pricing before launch because provider plans can change.

Official documentation:

- https://developers.cloudflare.com/r2/api/s3/
- https://developers.cloudflare.com/r2/pricing/

Typical R2 values:

```env
S3_REGION="auto"
S3_ENDPOINT="https://YOUR_ACCOUNT_ID.r2.cloudflarestorage.com"
S3_BUCKET="caleb-portfolio"
S3_ACCESS_KEY_ID="YOUR_R2_ACCESS_KEY"
S3_SECRET_ACCESS_KEY="YOUR_R2_SECRET"
S3_PUBLIC_BASE_URL="https://images.yourdomain.com"
S3_FORCE_PATH_STYLE="false"
```

Create an R2 API token with Object Read & Write access for only the required bucket when possible. Configure a public custom domain or other public read path for the bucket, then use that URL for `S3_PUBLIC_BASE_URL`.

# Security implementation

The project includes these baseline controls:

- Admin pages are protected server-side.
- Admin CRUD Server Actions call an authorization check before modifying data.
- Admin passwords are hashed with bcrypt using cost 12.
- Session tokens are random 256-bit values.
- Only session-token hashes are persisted to PostgreSQL.
- Authentication cookie is HTTP-only.
- Cookie uses `SameSite=Lax`.
- Cookie uses `Secure` in production.
- Server Actions are used for mutations where possible, benefiting from Next.js origin checks and same-origin form patterns.
- Admin image upload requires an authenticated session.
- Zod validates public forms and core CMS forms server-side.
- Blog Markdown is rendered without enabling arbitrary raw HTML, reducing rich-content XSS exposure.
- Credentials are read from environment variables.
- `.env*` secrets are excluded from Git.
- Admin routes are disallowed in `robots.txt` and have no-index metadata.
- Database relationships preserve booking history.
- Active booking slots have a unique database constraint to protect against race-condition double bookings.

For a high-risk or multi-admin application, add MFA, rate limiting, audit logging and a managed identity provider. This portfolio is intentionally kept simple for a single owner.

# Troubleshooting

## `DATABASE_URL is not configured`

Confirm `.env` exists in the project root and contains:

```env
DATABASE_URL="postgresql://..."
```

Restart `npm run dev` after changing `.env`.

## Prisma client import/generation errors

Run:

```powershell
npm run db:generate
```

Then restart the development server.

## `P1001` / cannot reach database

Check:

- PostgreSQL service is running
- hostname is correct
- port is correct
- password is correct
- database exists
- managed database firewall/network settings allow the connection

For local PostgreSQL, confirm port `5432` unless you selected another port during installation.

## Migration errors on a fresh local database

Check migration status:

```powershell
npx prisma migrate status
```

Then apply:

```powershell
npm run db:deploy
```

Do not run destructive reset commands against production.

## Admin login fails after database setup

Create/reset the admin explicitly:

```powershell
npm run create-admin -- caleb@example.com "New-Strong-Password-Here"
```

## Image upload works locally but not on Vercel

Production must use:

```env
IMAGE_STORAGE_MODE="s3"
```

Then check all S3 environment variables and verify the bucket has a public read URL for uploaded images.

## Image uploads return `Unauthorized`

Log into `/admin` again. Upload routes require a valid admin session.

## Booking date has no available times

Check:

- the weekday is active in `/admin/availability`
- start/end time are valid
- slot duration fits inside the time window
- the date is not blocked
- slots have not already been reserved

## Service cannot be deleted

If bookings reference the service, the CMS intentionally blocks deletion. Unpublish the service instead so historical bookings keep their service relationship.

## `npm install` fails on Windows around bcrypt

First confirm you are using a supported Node.js LTS version. Delete `node_modules` and reinstall:

```powershell
Remove-Item -Recurse -Force node_modules
Remove-Item package-lock.json -ErrorAction SilentlyContinue
npm install
```

Avoid switching to plaintext passwords or removing bcrypt to bypass an installation problem.

# Maintenance practices

Before changing the Prisma schema:

1. Create a database backup/snapshot.
2. Modify `prisma/schema.prisma`.
3. Create a migration in development.
4. Review the generated SQL.
5. Test locally.
6. Commit the migration.
7. Apply with `prisma migrate deploy` in production.

For content backups, include PostgreSQL backups and object-storage images. GitHub source control does not contain the live CMS content.
